# Conformance

What oneyaml-go is measured against, the latest results, and every case it is known not to pass.

The library targets YAML 1.2 with the Core schema. It is scored against the official [yaml-test-suite](https://github.com/yaml/yaml-test-suite), release `data-2022-01-17`, plus a set of cases written for the oneyaml family that cover edits, patches, writing, safety and diagnostics. Both run through the conformance kit of the oneyaml family, [oneyaml-kit](https://github.com/recursive-ai-oss/oneyaml-kit), which drives the library through its public API: `Parse`, `Unmarshal`, `Marshal`, `ApplyPatch` and `ApplyMergePatch`. The kit holds the cases, the corrected expectations and the adapter for this library. From a checkout of the kit, run `bin/kit fast --adapter oneyaml-go` with `KIT_ONEYAML_GO_SRC` set to a checkout of this repository.

The tests in this repository that run the kit's cases through the library also run in CI, on every push to `main` and every pull request, against a pinned kit revision, so a change that breaks a kit case fails CI. Locally they are skipped unless `ONEYAML_KIT` names a kit checkout.

### How to read the table

- **Loose** counts the outcome only: valid input must give exactly the expected events, value or bytes, and invalid input must be reported as an error.
- **Strict** counts everything the case states. For invalid input that includes the error category and position, and the events emitted before the error.
- **Strict, corrected** judges the cases where the upstream expectation is wrong against the kit's corrected one. The kit lists the corrections and their reasons.
- **Unsupported** and **Strict only** count cases the adapter cannot judge. They are not passes.

### Invalid input and strict events

For invalid input, the Loose column counts the inputs the library rejects. The Strict column also compares the events emitted before the error, and `Parse` returns no partial document, so the kit's adapter has no events to hand over for a failing input and the strict check cannot count a pass for that row. This is a gap in what the public API exposes, not a case the library accepts. The error category and position are checked by the kit's diagnostics cases, which have rows of their own.

## Known deviations

The cases below are the ones the library does not pass. Each one is a difference in the Go value `Unmarshal` into `any` produces, not in what the parser accepts; the `Document` and `Node` API keep the information.

| Case | What happens | Where to get the full information |
|---|---|---|
| `yts:UGM3@value` | The suite's `in.json` records `450` for the scalar `450.00`; the Core schema reads it as the float `450.0`. The kit's corrected expectation agrees with the library (see Strict, corrected). | none needed |
| `own:schema/unresolved-tag-is-kept` | A local tag the schema does not know, such as `!color red`, reads as the string `red`. The tag is dropped from the generic value. | `Node.ExplicitTag`, `Node.TagAsWritten` |
| `own:schema/local-tag-on-a-collection-is-kept` | A local tag on a mapping or sequence is dropped from the generic value. | `Node.ExplicitTag` |
| `own:schema/global-tag-uri-is-kept` | A global tag URI such as `tag:example.com,2000:shape` is dropped from the generic value. | `Node.ExplicitTag` |
| `own:schema/code-constructing-tags-are-kept-or-refused` | A tag such as `!!python/object/apply:os.system` is dropped and the value read as plain data. Nothing is constructed or run. | `Node.ExplicitTag` |
| `own:schema/mapping-as-a-mapping-key` | `Unmarshal` into `any` refuses a mapping used as a key, because a Go map cannot hold it. | `Parse`, `Node.Entry` |
| `own:schema/sequence-as-a-mapping-key` | The same for a sequence used as a key. | `Parse`, `Node.Entry` |

Each of these appears twice in the table of deviations in the report above, once for the loose check and once for the strict one. The kit fails the run if a case fails that is not on this list, and fails it if an entry on the list starts to pass, so the list cannot go stale unnoticed.

## What the results do not say

- The suite covers the grammar. It is not a benchmark.
- A pass is a pass of the kit's checks at the revision shown. It is not a proof of conformance for input the suite does not contain; the library is also fuzzed.
- The kit's own cases were written for this project family. They are a stricter and broader check than the upstream suite alone, and they are the project's judgment of what correct behaviour is where the specification leaves a choice, such as where a new mapping key goes.
